## 三、两个产物的区别

| | `news.json` | `brief.json` |
|---|---|---|
| 谁生成 | `aggregate.mjs` | Agent 手写 |
| 能否重跑覆盖 | 能，随时重跑 | **不能**，写了就是定稿 |
| 条数 | 200+ | 3–5 条 picks + 扫读清单 |
| 含判断吗 | 不含（只有 `relatedSources` 计数） | 含（评级、`why`、冲突说明） |
| 改了会怎样 | 影响候选池 | 影响所有产物 |

**关键：判断只存在 `brief.json` 里。** 渲染脚本不产生任何判断，也不做任何兜底改写。
`build-pptx.mjs` 里连「如果字段缺失就显示暂无」这种兜底都尽量少写——
缺字段就该报错，让问题暴露在生成阶段，而不是悄悄渲染出一个空洞的 PPT。

## 三·补 · 三层校验（v0.3.0 起）

产物质量由三道闸门守住，各管一层，不重叠：

| 闸门 | 时机 | 管什么 | 失败表现 |
|---|---|---|---|
| `validate-brief.mjs` | 写完 `brief.json`，渲染前 | **业务规则**：评级与信源数自洽、`why` 不写空话、日期合理 | exit 1，列出违规条目 |
| `build-pptx.mjs` 内置溢出校验 | 写盘前 | **版式容量**：有没有文本框装不下 | exit 1，**不产出文件** |
| `test-render.mjs` | 改过渲染脚本后 | **回归**：页数公式、fail-fast 行为、校验器本身有没有失效 | 11 项断言，报告带时间戳 |

顺序上：**先校验业务，再校验版式，最后才写盘**。

关键点在于第一道管的是「渲染不会失败、但产出违规日报」的问题——
标 A 却只有 1 个源、全转载却标 B 这类。这类问题**产出的 PPT 看起来完全正常**，
只有机械校验守得住。

## 三·补2 · 触发层（v0.4.0 起）

链路的两端是两个「机器」环节，中间的判断层只有 Agent（或人）能做。
所以触发方式有两种，走的是**同一条链路**：

```
        ┌─ 定时：每天 07:00（cron / Vercel Cron）────┐
触发 ───┤                                            ├──▶ ① 抓取 → ② 选稿 → ③ 渲染 → ④ 打包
        └─ 手动：serve.mjs / 页面按钮 / --selftest ───┘
                        ↑
              单并发队列（两个任务并行渲染会互相覆盖文件）
```

`scripts/serve.mjs` 是手动入口：零第三方依赖（只用 `node:http`），
把上面四步暴露成 7 个接口，四步进度如实回传，**只监听 `127.0.0.1`**。

它同时是**降级点的守门人**：手动触发时若 `data/<date>/brief.json` 还不存在
（Agent 还没跑），它会调 `draft-brief.mjs` 产出 `brief.draft.json`（带 `draft: true`），
渲染器据此在封面 + **每一页**页脚 + 文件名上标注「机器草稿」，
且**永不复用正式产物的文件名** —— 一次「随手生成草稿」不会静默覆盖 Agent 的正式 PPTX。

> 设计原则没变：机器只做机器能确定的事。草稿的评级上限是 B（A 级要核验一手官方材料），
> 不写点评、不查重、不给冲突结论。**宁可明显标着「这是草稿」，也不假装有判断。**

详见 [09-手动触发生成服务.md](./09-手动触发生成服务.md)。

## 四、为什么渲染脚本不做兜底

```js
// build-pptx.mjs 的写法（刻意的）
if (!existsSync(briefFile)) {
  console.error(`[build-pptx] 找不到选稿文件：${briefFile}`)
  process.exit(2)        // 硬失败，不生成半个文件
}
```

对比另一种常见写法（我们不这么干）：

```js
// ❌ 不要这样
const picks = brief.picks || []        // 静默变成空数组
const title = pick.title || '（暂无）'  // 渲染出一页「（暂无）」
```

后者会让一份「什么都渲染成功、但内容全空」的 PPT 顺利产出，
而流水线返回 exit 0，看起来一切正常。**宁可硬失败。**

这条纪律对应 `SKILL.md` 里的第 2 条：

> 宁可不产出，也不产出「生成一半的 PPT」。渲染失败 → 输出 Markdown 并显式写明降级原因。

## 五、源健康度机制

`aggregate.mjs` 会对每个源记账，写进 `sourceHealth`：

- 连续失败会标记，但**不阻断整批**
- 单源失败 → 日报标注「今日 X 源不可达」，继续
- **≥3 源失败 → 停下来报故障，不出日报**

为什么是 3：10 个源里挂 1–2 个，候选池仍然够；挂 3 个以上，
多源交叉验证的基础就塌了——此时出的日报**看起来正常但实际上失去了可信度依据**，
这比不出更危险。

## 六、时间处理

三个文件各自负责一件事，不要混：

| 文件 | 职责 |
|---|---|
| `date-util.mjs` | 今天是几号（**本地时区 GMT+8**） |
| `time-utils.mjs` | 这条新闻什么时候发布的 |
| `storage.mjs` | 往 `data/YYYY-MM-DD/` 写，原子写盘 |

**绝对不要用 `toISOString()` 算日期。** UTC 会把 GMT+8 凌晨的数据写进前一天，
表现为「脚本跑完了，但今天的文件夹是空的，昨天的文件更新了」。
这个坑排查成本很高，因为它看起来像抓取失败。

## 七、依赖图

```
aggregate.mjs
  ├── date-util.mjs
  ├── storage.mjs
  ├── time-utils.mjs
  ├── config/sources.json
  └── (零第三方依赖，只用 Node 内置 fetch)

build-pptx.mjs
  └── pptxgenjs          ← 唯一第三方依赖

brief-to-md.mjs
  └── (无依赖)
```

**抓取链路零依赖**是刻意的：只要 4 个文件 + 1 个 config，拷到任何地方都能跑。
