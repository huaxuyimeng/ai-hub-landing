# 00 · 设计思路

> 这份文档回答的是「为什么这么设计」，不是「怎么用」。
> 用法见 [02-每日作业手册.md](./02-每日作业手册.md)，字段规范见 [04-数据契约.md](./04-数据契约.md)。
> 建立日期：2026-09-14

## 一、先界定：我们要解决的到底是不是「做个 PPT」

不是。

如果目标是「把新闻排成好看的幻灯片」，那这件事三年前就被解决了，而且现在卷到没有意义。
2026 年 9 月的赛道现状（本次实测调研）：

| 项目 | Star | 在卷什么 |
|---|---|---|
| banana-slides | 15.5k | 排版 / 模板 |
| PPTist | 9.3k | 在线编辑体验 |
| dashi-ppt-skill | 7.2k | 一句话生成 PPT |

全部在卷「生成得像不像人做的」。这个方向上，我们既没有先发优势，也没有资源优势，
**做出来的最好结果也只是第 4 个 banana-slides**。

所以真正的问题要换一个问法：

> 每天有 200+ 条 AI 新闻涌进来，其中**有多少条是可以相信的**？
> 我凭什么把某 5 条放进日报，而不是另外 5 条？

这才是这个工具存在的理由。

## 二、唯一的护城河：可信度，而且要能自证

本项目唯一站得住的差异点，是**对每条新闻给出可追溯的可信度判断**。具体拆成三件事：

1. **多源交叉验证** —— 10 个信源，跨中英文，不是单一信息流
2. **置信度 A/B/C/D** —— 规则公开、可复算，不靠感觉
3. **显式声明缺失** —— 「这条只有一家在说，我们没核实」要写进产物，而不是藏起来

竞品在这三项上是 0。而这三件事我们已经跑通了。

### 为什么必须写进产物而不是留给自己知道

因为一旦「置信度」只是 Agent 脑中的一个念头，它就会在下一轮被遗忘、被美化、被默认的乐观替代。
写进 `brief.json`、印在 PPT 第 3 页、出现在每条要闻的角标上，它就变成了一个**被约束的量**。

同理，PPT 最后一页那句免责声明不是客气话：

> 本 PPT 的结论未经人工逐条核实。置信度只反映「有多少个相互独立的信源在说同一件事」，
> 不反映这件事本身是否为真。

这是刻意的设计——**声明能力的边界，本身就是可信度的一部分**。
一个敢说「我没核实」的系统，比一个假装什么都核实过的系统更值得信。

## 三、三段分工：机器 / 我 / 机器

```
① 机器做（aggregate.mjs）        ② 我做（判断层）              ③ 机器做（渲染）
抓 10 源 → 归一化 → 去重        外部核验 → 查重 → 选题        brief.json → .pptx / .md
→ 多源关联 → 分类 → 归档        → 定级 → 写「为什么值得关注」
       ↓                                ↓                            ↓
   news.json                       brief.json                   .pptx + .md
 （机器产物，可重跑）         （唯一真相源，人工可改）       （纯渲染，不含判断）
```

### 为什么切成三段，而不是一条龙跑完

因为**中间那段机器做不了**。

- 第 ① 段：确定性工作，抓、洗、去重、算多源。机器做，可重跑，错了重跑一次就好。
- 第 ② 段：判断工作。需要读原文、搜一手来源、识别「这 20 家是不是都在抄同一篇」。
- 第 ③ 段：确定性工作。给什么渲染什么。

如果让机器一路跑到底，第 ② 段就会被「relatedSources 数量」这种代理指标偷换掉，
产出的日报看起来很严谨（每条都标了 5 个来源），实际上可能是 5 家转载。

### 一个真实案例，说明第 ② 段为什么不可替代

2026-09-14 那期第 5 条「Mecka AI 估值三个月从 6000 万到近 5 亿」：

- 聚合层判定：**多源**，TechCrunch + 多家转载，relatedSources 数量很好看
- 人工核验后：**所有报道都溯源到 TechCrunch 同一篇独家**，引述的是「两位知情人士」
- 结论：从「看起来很硬」降到 **C**

这一步是整条流水线唯一真正产生价值的地方。**转载数量 ≠ 独立信源数量**——
这条规则写在 `SKILL.md` 里，是硬规则，不许为了「看起来更可信」而放宽。

宁可多标几个 C。

## 四、为什么 `brief.json` 必须是唯一真相源

早期版本（`ai-news-daily`）的问题是：选稿逻辑散落在脚本里，文案写在渲染代码里。
后果是——当 PPT 里某句话被质疑时，回溯路径是发散的：

- 这句话是脚本算出来的？还是写死的？
- 要改，是改脚本、改模板、还是改数据？
- 改完渲染，Markdown 版要不要同步改？

现在的约定：

> **`data/YYYY-MM-DD/brief.json` 是唯一真相源。渲染脚本只做渲染，不做任何判断。**

带来的好处：

1. **回溯路径唯一** —— 内容错了，只可能是 `brief.json` 错了
2. **多产物天然一致** —— PPT 和 Markdown 读同一份数据，不会打架
3. **人工可干预** —— 想改一个字，改 JSON，重跑渲染，不用碰代码
4. **可 diff** —— 两天的 `brief.json` 一比，就知道选稿口味有没有漂移

代价是：Agent 每次要手写一份结构化 JSON，比直接写文案麻烦。
这个代价是**故意付的**——麻烦会逼你想清楚每个字段，而不是糊一段漂亮话。

## 五、置信度规则的来历

### 规则本身

| 等级 | 判定 |
|---|---|
| **A 极高** | ≥3 个**相互独立**的信源，且可追溯到一手官方材料 |
| **B 高** | 2 个独立信源，或 1 个信源 + 一手官方材料 |
| **C 中** | 单一信源；或**多家转载同一家独家** |
| **D 存疑** | 关键数字互相矛盾，或全部可溯源到同一原始信源且无官方确认 |

### 三个刻意的设计选择

**1. 只按「独立信源数」判定，不做人工核实**

这是刻意设计，不是偷懒。原因：
- 人工核实一条新闻需要读原文、找一手、比对数字，代价极高，每天 5 条不可能真做
- 如果宣称「已人工核实」但只做了 30%，那比不宣称更糟——**这是伪装成确定性的不确定性**
- 相反，「我只数了有几个独立信源在说」是一个**可以被读者自己复算的量**

所以 PPT 上直接印着这句话。诚实地标注方法论的边界，比含糊地宣称权威要好。

**2. 转载不算独立信源**

见上文 Mecka 案例。这条规则执行起来会显得「评级偏低」，
但评级偏低是**安全的方向**——读者自己去核实了发现其实是真的，损失只是虚惊；
反过来，评级偏高导致读者不核实就引用，损失是错的结论被传播。

**3. 规则公开在产物里**

置信度量表作为 `confidenceScale[]` 字段写进 `brief.json`，渲染成 PPT 第 3 页。
读者不需要信任我们，他自己就能判断这个评级合不合理。

## 六、多源关联阈值为什么是 3

判定「两条新闻是不是同一件事」，用共享实体 token 数。阈值是实测调出来的，不是拍脑袋：

| 阈值 | 被判为多源的条目占比 | 评价 |
|---|---|---|
| 2 | 47.2% | 虚高——几乎一半条目都被算成多源，失去区分度 |
| **3** | **18.5%** | **合理** |
| 4 | 10.6% | 偏严——漏掉真实的多源报道 |

这个值硬编码在 `config/sources.json` 的 `crossSourceTokenThreshold`，
并且把实测依据作为 `_thresholdNote` 写在同一文件里。

> 为什么把依据写进 config：因为半年后一定会有人（包括我）想改这个值。
> 如果没有依据，改动就是凭感觉；有了依据，改动前至少要先重跑一次测量。

## 七、形态决策：为什么是纯 Node 脚本

| 候选方案 | 为什么没选 |
|---|---|
| DSH / Cordis 插件 | 外人没有 DSH 环境，clone 下来跑不起来。旧版 `ai-news-daily` 就是这个形态，等于不可分发 |
| Web 服务 | 多一套部署负担，而需求是「每天跑一次」，不是「随时可访问」 |
| 单文件脚本 | 会有 1000+ 行，改一个源要读全文件 |
| **纯 Node 脚本 + 配置分离** | **选它** |

关键约束：**只依赖一个公开 npm 包（pptxgenjs）**，且抓取部分零第三方依赖（只用 Node 内置 fetch）。

这意味着：

- 只想要数据不要 PPT 的人，拷 4 个文件就能跑，不用 `npm install`
- 整个目录拷进任何 Node ≥22.6 项目，路径全基于 `__dirname` 解析，不用改
- 没有框架、没有构建步骤、没有环境变量

### 为什么渲染只留 pptxgenjs

旧版有双产线：正式线用 `@tencent/slidep`（内部包），预览线用 pptxgenjs。
**内部包对外人不可用**——这意味着 clone 仓库的人连 `npm install` 都过不去。
所以可移植版本**砍掉正式线**，只留公开包。

代价是渲染精细度下降。这个代价是值得的：**一个能跑起来的 80 分，胜过一个跑不起来的 95 分。**

## 八、移植纪律：为什么不重写抓取代码

`aggregate.mjs` / `date-util.mjs` / `storage.mjs` / `time-utils.mjs` 是从旧项目
**原样拷贝，一行没改**。

理由：这些代码已经跑了一段时间，边界情况（RSS 变体、HTML 实体、时区、重复条目）
在实战里被磨过。重写的收益是「代码更整洁」，风险是「引入新 bug 且无人发现」。

**已验证的逻辑不要重写。** 要改的是形态和依赖，不是已经正确的算法。

新增的部分只有两个渲染脚本，它们是新的、可独立测试的。

## 九、明确的取舍：我们放弃了什么

写清楚不做什么，比写清楚做什么更重要：

| 放弃 | 原因 |
|---|---|
| 精美的排版与动画 | 卷不过 15.5k star 的专用项目，且不是价值所在 |
| 全自动（无人参与） | 第 ② 段判断机器做不了，硬做就是拿代理指标冒充判断 |
| 实时性（分钟级） | 新闻窗口以天为单位，每天一次足够；实时会逼你放弃核验 |
| 全量覆盖 | 只要 3–5 条。**宁可少而准，不要多而虚** |
| 人工逐条核实 | 代价不可承受，且宣称了做不到就是欺骗。改为公开方法论边界 |
| 内部渲染包 | 对外不可分发 |

## 十、这套设计还没解决的问题（诚实清单）

1. **分类靠关键词，误召回严重**。`AI Coding` 分类里混进大量含 "agent" / "token" 的泛 AI 条目，
   2026-09-14 实测 88 条里真正相关的不到 20 条。目前靠第 ② 段人工筛，没有自动化。
2. **查重靠人工比对**。读历史 `brief.json` 和历史 md 逐条比，没有主题指纹。跑久了会越来越慢。
3. **`why` 字段质量依赖当期 Agent 的水平**，没有校验机制。写得好不好全看这一轮。
4. **没有回归测试**。渲染脚本改一行可能悄悄破坏版式，只能靠生成后打开看。
5. **信源中英文不平衡**（中文 6 / 英文 4），且 tier 3 的三家英文源都是聚合性质。

这些都知道，没做。列在这里是为了避免半年后误以为「当初设计得很完善」。

---

## 附：一句话总结这套设计

> 机器负责不知疲倦地抓和不知疲倦地渲染，
> 人（Agent）只负责中间那件机器做不好的事——**判断这条能不能信**，
> 并且把判断的依据和边界，老老实实写进产物里。
