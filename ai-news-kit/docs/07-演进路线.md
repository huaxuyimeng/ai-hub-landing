## P0 · 应该尽快做

### ✅ 1. `brief.json` 的自动校验（已完成，v0.3.0）

```bash
node scripts/validate-brief.mjs --date 2026-09-14
```

**结构校验**：顶层字段、date 格式、confidenceScale 必须 A/B/C/D 有序、picks 3–5 条、每条必填字段。
**业务规则**（真正的价值所在）：

| 规则 | 级别 |
|---|---|
| 标 A 但独立信源 <3 | ❌ 错误 |
| 标 A 但无一手来源 | ❌ 错误 |
| 标 B/C/D 但**所有来源都是转载** | ❌ 错误（按规则只能定 C） |
| `publishedAt` 晚于日报日期 | ❌ 错误 |
| `why` <40 字 | ❌ 错误 |
| `why` 含空话（值得关注/重大突破/标志着…） | ⚠️ 警告 |
| `sources[0]` 未标注一手来源 | ⚠️ 警告 |
| `conflicts` 为空 | ⚠️ 警告 |
| 本期无 C/D 级条目 | ⚠️ 警告（防止评级被系统性放宽） |

**零新依赖**：规则内联实现，不引入 ajv —— 保持「抓取链路零第三方依赖」的设计。

### 2. 主题指纹查重（未做）

**问题**：查重现在靠人读历史 `brief.json`，跑一个月后历史文件变多，会越来越慢。

**做法**：给每条 pick 存一组 `topicTokens`（主体 + 动作 + 对象），
新候选与历史做 Jaccard 相似度，>0.6 自动标为「疑似重复」交给人工确认。

**注意**：只做**提示**不做**自动排除**。误杀一条真新闻的代价 > 人工看一眼的代价。

### ✅ 3. 渲染回归测试（已完成，v0.3.0）

```bash
node scripts/test-render.mjs     # 或 npm test
```

11 项断言，报告写入 `tests/test-report.txt`（**带生成时间戳**）：

| # | 断言 |
|---|---|
| 1–4 | 正常渲染 exit 0 · 产出文件 · 体积 >40KB · **页数 == 3+picks+2** |
| 5–7 | 超长内容 exit 1 · **溢出时不产出文件** · 报错列出溢出位置 |
| 8 | brief 不存在 → exit 2 |
| 9–11 | validate-brief：合法通过 · 抓到「标A但源不足」· 提示空话 why |

> 第 6 项是「宁可不产出，也不产出生成一半的 PPT」这条纪律的**机械化验证**——
> 纪律不能只写在文档里，要有测试守住。

### ✅ 4. 手动触发（已完成，v0.4.0）

**问题**：原来只有定时（07:00）。想看今天的情况、开会前临时要一版、改完配置想立刻验证，
都得自己敲四条命令拼参数 —— 也就意味着「只有写脚本的人能用」。

**做法**：`scripts/serve.mjs` 把四步链路暴露成 HTTP 接口（零依赖），
本机起一个只监听 `127.0.0.1` 的服务；前端（`aihub/landing/briefing.html`）点按钮即可触发，
四步进度如实回传。没有 Agent 选稿时自动降级为**机器草稿**（`draft-brief.mjs`），
并在 PPT 封面 + **每一页**页脚 + 文件名上标注，绝不与正式产物混同。

**顺带解决**：手动触发的存在让「定时只跑到 Agent 选稿」成为可行分工 ——
渲染只要 0.3 秒，交给人和按钮决定就行，不必塞进 cron。

**遗留**：服务无鉴权（有意为之，只监听本机）；草稿的跨源聚簇仍是标题级近似匹配，
做不到语义级 —— 那正是 Agent 该做的事，不是机器的。

## P1 · 值得做

### 4. 分类改语义化

**问题**：关键词误召回严重。

**做法**：用 embeddings 或小模型做零样本分类。
**代价**：引入模型依赖，破坏「抓取零依赖」的设计。

**折中方案**：作为**可选层**——默认关键词分类，
配了 API key 才启用语义分类。不加依赖，只加可选增强。

### 5. 一手来源自动探测

**问题**：核验要人工 WebSearch。

**做法**：对每条候选，先尝试：
1. 从 `summary` 里抽公司名/产品名
2. 构造候选官网域名，HEAD 请求探测
3. 命中就作为一手来源候选

**期望**：能覆盖 30%–40%，剩下的仍要人工。
**价值**：不是替代人工，是减少人工的机械劳动。

### 6. 历史趋势追踪

**问题**：现在是「每天一份孤立日报」，看不出趋势。

**做法**：维护一个 `data/topics.json`，记录每个主题首次出现日期、
每次出现的 `lv`、涉及信源。跑一个月后能回答：
「这个赛道本周升温了吗」「哪家媒体总是第一个报」

**价值**：从「日报」升级为「情报」。

## P2 · 想做但不急

### 7. 多产线渲染

现状只有 pptxgenjs。可以加：
- HTML 版（可交互、可搜索）
- PDF
- 飞书 / 企业微信卡片

**前提**：先把渲染器抽象成接口，不要让第二个渲染器再抄一遍版式代码。

### 8. 信源权重

现在所有源等权。实际上 MIT TR 的深度报道 >> 某个聚合站的 30 字摘要。
可以给 tier 1/2/3 配不同权重，影响候选排序（**不影响置信度评级**——评级只看独立性）。

### 9. 中英文信源再平衡

现状中文 6 / 英文 4，且三家英文源都是聚合性质。
缺的是**有独立采访能力的英文科技媒体**（The Information、The Verge 深度线）。

## 明确不做的

| 不做 | 原因 |
|---|---|
| 精美排版 / 动画 | 卷不过 15.5k star 的专用项目，不是价值所在（见 [00-设计思路](./00-设计思路.md)） |
| 全自动无人参与 | 判断层机器做不了，硬做就是拿代理指标冒充判断 |
| 分钟级实时 | 新闻窗口以天为单位；实时会逼你放弃核验 |
| 全量覆盖 | 只要 3–5 条。宁可少而准 |
| 宣称「人工逐条核实」 | 做到 30% 却宣称 100%，是伪装成确定性的不确定性 |

## 排序依据

优先级按 **「出错代价 × 发生频率」÷ 实现成本** 排：

- `brief.json` 校验：出错会直接产出错误日报，每天都可能发生，实现只要半天 → **P0**
- 主题指纹：出错会重复推送，频率中等，实现一天 → **P0**
- 渲染回归：出错只影响版式不影响内容，但改渲染时必现 → **P0**
- 语义分类：出错只是候选池脏一点，已有人工兜底 → **P1**
